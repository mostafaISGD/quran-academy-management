2. Database Schema — تفصيلي

الترميز: PK = Primary Key، FK = Foreign Key، UQ = Unique، NN = Not Null. النوع الافتراضي لأي id هو BIGINT (auto-increment) ما لم يُذكر غير ذلك. جميع الجداول تحتوي created_at, updated_at (TIMESTAMP) ما لم يُذكر خلاف ذلك، ومعظمها deleted_at (TIMESTAMP NULL) لدعم Soft Delete.

4. Use Cases الرئيسية

UC-01: تسجيل طالب جديد من Lead

  • الفاعل: موظف خدمة العملاء
  • الشرط المسبق: يوجد Lead بحالة trial_completed ونتيجة تقييم ready_to_subscribe
  • الخطوات:
    1. الموظف يفتح الـLead ويضغط "تحويل إلى طالب"
    2. النظام ينشئ student جديد ويربطه بـ lead_id (لا يُحذف الـLead)
    3. الموظف يختار subscription_plan والمعلم
    4. النظام يُنشئ subscription بـ price_at_purchase منسوخ من الخطة الحالية
    5. الموظف يسجل payment أول
    6. النظام يُحدّث حالة الـLead إلى converted
  • الشرط اللاحق: الطالب نشط وله اشتراك ساري، وجاهز لجدولة الحصص
  • قواعد العمل: الاشتراك لا يُنشأ بدون Payment ناجح أو تسجيل صريح "دفع آجل" من مدير مخوّل

UC-02: جدولة حصص متكررة

  • الفاعل: موظف/إدارة
  • الخطوات:
    1. اختيار الطالب + المعلم + الأيام والوقت (مثال: سبت/اثنين/أربعاء 7:00 مساءً بتوقيت الطالب)
    2. النظام يحوّل الوقت إلى UTC ويتحقق من teacher_availability وعدم وجود تعارض في lessons
    3. عند عدم وجود تعارض: يُنشئ سلسلة حصص بنفس recurrence_group_id حتى نهاية subscription.end_date أو حتى استنفاد lessons_allowed
    4. عند وجود تعارض: يعرض رسالة "المعلم لديه حصة أخرى في هذا التوقيت" مع اقتراح أقرب وقت متاح
  • الشرط اللاحق: حصص بحالة scheduled مرتبطة بالاشتراك

UC-03: إجراء الحصة وتسجيل النتائج (من جهة المعلم)

  • الفاعل: المعلم
  • الخطوات:
    1. المعلم يفتح "حصص اليوم" ويضغط "دخول الحصة" (فتح رابط Zoom/Meet خارجيًا)
    2. بعد انتهاء الحصة، يضغط "إنهاء الحصة"
    3. يسجل الحضور (lesson_attendance)
    4. يسجل الحفظ الجديد والمراجعة والتقييم (memorization_records)
    5. النظام يُنشئ سجل progress_records تلقائيًا ويُحدّث students.current_juz/current_surah
    6. إذا subscription.billing_model للمعلم = per_lesson: النظام يُنشئ teacher_earnings بقيمة lesson_rate
    7. حالة الحصة تتغير إلى completed، وsubscriptions.lessons_used += 1

UC-04: غياب المعلم وإنشاء حصة تعويضية

  • الفاعل: الإدارة أو النظام تلقائيًا بعد مرور وقت الحصة بدون تسجيل
  • الخطوات:
    1. تُسجَّل الحصة الأصلية بحالة teacher_absent
    2. النظام لا يخصم هذه الحصة من lessons_used
    3. الإدارة تُنشئ حصة جديدة بـ is_makeup_for_lesson_id = معرّف الحصة الأصلية
    4. الحصة التعويضية الجديدة عند اكتمالها هي التي تُخصم من الرصيد
  • قاعدة العمل الحرجة: أي حصة لها is_makeup_for_lesson_id غير NULL لا تُنشئ خصمًا مضاعفًا؛ فقط إكمالها الفعلي يُحتسب.

UC-05: تجديد اشتراك شهري منتهي

  • الفاعل: النظام (تلقائي) + موظف الحسابات
  • الخطوات:
    1. Cron يومي يفحص subscriptions.end_date خلال 3 أيام القادمة
    2. يُرسل notification (event_type=subscription_expiring) للطالب/ولي الأمر وللإدارة
    3. عند انتهاء الاشتراك فعليًا وعدم التجديد: status → expired، ويتوقف إنشاء حصص جديدة عليه
    4. عند دفع الطالب: يُنشأ subscription جديد (وليس تعديل القديم) — الحفاظ على السجل التاريخي

UC-06: محاسبة معلم "بالحصة" آخر الشهر

  • الفاعل: محاسب
  • الخطوات:
    1. فتح /api/teachers/{id}/earnings لفترة الشهر
    2. النظام يجمع كل صفوف teacher_earnings (lesson_earning + bonus + deduction + advance) للفترة
    3. يُنشئ teacher_payment بـ gross_amount المحسوب
    4. المحاسب يسجل الدفعة الفعلية (قد تكون جزئية) → paid_amount, remaining_amount يُحدَّث تلقائيًا
  • ملاحظة: معلم monthly لا يمر بنفس الحساب — gross_amount = teachers.monthly_salary مباشرة، والحصص تُسجَّل لأغراض التقارير فقط

UC-07: طالب اشتراكه شهري ومعلمه بالحصة (السيناريو المركب)

  • الفاعل: النظام (منطق ضمني، لا تدخل يدوي إضافي)
  • يوضح استقلالية النموذجين:
    • عند اكتمال كل حصة: subscriptions.lessons_used += 1 (يؤثر فقط على رصيد الطالب)
    • وبشكل مستقل تمامًا: يُنشأ teacher_earnings بقيمة teacher.lesson_rate (يؤثر فقط على مستحقات المعلم)
    • الجدولان لا يتشاركان أي حقل أو منطق حسابي مشترك؛ التغيير في أحدهما لا يُعدّل الآخر

UC-08: تسجيل عملية دفع واسترجاعها

  • الفاعل: محاسب / مدير
  • الخطوات:
    1. تسجيل payment بحالة completed
    2. عند الحاجة لاسترجاع: لا حذف — إنشاء refund مرتبط بـ payment_id مع سبب
    3. النظام يُحدّث payments.status → voided تلقائيًا عند اكتمال الاسترجاع
    4. يُسجَّل الإجراء كاملًا في audit_logs (من قام بالإجراء، القيمة القديمة/الجديدة)

UC-09: حجز وإجراء تقييم تجريبي (Trial Assessment)

  • الفاعل: موظف خدمة العملاء ثم المعلم
  • الخطوات:
    1. الموظف يُنشئ assessment مرتبط بـ lead_id مع معلم ومعاد
    2. النظام يُنشئ meeting_link للتقييم
    3. بعد الجلسة، يدخل المعلم الدرجات والمستوى المقترح والنتيجة (result)
    4. عند result = ready_to_subscribe: تتفعل خطوة UC-01

UC-10: تعارض في الجدولة (Conflict Detection)

  • الفاعل: النظام (تحقق تلقائي عند أي إنشاء/تعديل حصة)
  • المنطق: قبل حفظ أي lesson جديدة أو معدَّلة، يتحقق النظام من عدم وجود صف آخر بنفس teacher_id تتداخل فيه scheduled_start_at–scheduled_end_at مع حصة أخرى ليست cancelled. عند وجود تداخل → HTTP 409 مع تفاصيل الحصة المتعارضة.

5. ملاحظات تنفيذية ختامية

  • Timezone: كل الأوقات تُخزَّن UTC في قاعدة البيانات، وتُحوَّل للعرض فقط حسب users.timezone لكل طرف (طالب/معلم/إدارة).
  • Recurring Lessons: تُبنى فوق recurrence_group_id لتسهيل التعديل/الإلغاء الجماعي دون كسر الحصص الفردية المُعدَّلة يدويًا.
  • لا Migration مفاجئة لاحقًا: الحقول التي ذُكرت كإضافات محتملة (خصم الإخوة، الحصص الجماعية) يُفضَّل حجز أعمدة/جداول لها من الآن حتى لو لم تُفعَّل في V1، لتفادي إعادة هيكلة الجداول المالية لاحقًا.
